## 唯一权威与恢复顺序

PostgreSQL 保存任务身份、审批范围、Run、epoch、预算预占/结算、操作日志、收件箱、
事件游标和选中的 checkpoint/result hash。现有 Engine 持有单写者锁并负责这些业务写入。
CAS 保存内容，不选择权威；工作区 manifest、`context.json`、文件事件和模型摘要不能
授予 epoch、扩大 grant、释放未知费用或证明任务已完成。

1. 新进程打开同一 Engine；现有服务启动恢复将中断的 Run 暂停并使旧 epoch 失效。
   不能在仍持单写者锁的服务旁边启动第二个 Engine 写者。
2. 取 PostgreSQL 的注册信息、任务身份、固定 grant 和选中的 checkpoint。核对 CAS hash、
   task/run/workspace/repository 与原 manifest，不接受模型文字或任意本地 JSON 代替。
3. 先获取工作区文件锁，再检查/取得 Engine epoch。编辑对账与接管维持同一锁顺序，
   防止旧 Worker 核权后与新 Worker 抢写文件。
4. 对账已派发的编辑与受管命令，确认树来自本次待恢复的操作证据。未解释的树漂移、
   缺失产物、冲突前图像与未结算已发送调用均失败关闭；历史已知树不能直接授权回退。
5. 所有必需未知副作用解决后，接管同一个 Run 并取得新 epoch。Thread/Run 身份不变，
   截止时间、调用预算与费用预占不因重启重置。旧 epoch 的编辑、执行、结算、事件与完成写入被拒绝。
6. 由选中的循环 continuation 恢复原计划、基线文件、历史消息、验收与失败状态及指令水位。
   模型批次保留原 operation ID 和原请求，只更新受信 epoch 元数据；不从已变化的树重新编造旧请求。

循环 checkpoint 在基线前及每轮模型预占/发送前保存。模型请求包含原始消息、工具声明、
model/price/context revision 和请求树；状态包括既有回执与验证树、完整历史、修复轮数、
无进展状态、已应用指令水位。PG 原子选择 checkpoint 与水位，未被选择的 CAS 文件仅供审计。
部分工具完成后重启，先由日志对账得到可信当前树，再按原批次顺序复用已知工具结果；
只有该对账树可以解释原请求树与当前树的差异，任意手工漂移仍被拒绝。

## 操作与费用状态

| 已记录状态 | 恢复行为 | 禁止的行为 |
| --- | --- | --- |
| prepared，尚未发送 | 在同一 operation ID 下继续；核对相同输入与预占 | 换 ID 再扣预算或用不同请求覆盖 |
| known 模型结果 | 复用已持久化响应及原子结算，不再调用供应商 | 已知结算后重新付费、将旧响应冒称新请求结果 |
| dispatched/unknown 模型 | 保留预占并阻止继续发送；等待可信对账 | 自动退款、盲重试或凭摘要改为 known |
| known 工具/交互结果 | 复用相同操作的结果与计费单位，保持原顺序 | 重施补丁、重复等待已答问题、把缓存当新证据 |
| 无副作用读取未收回 | 当前权限与 epoch 复核后可重读 | 根据旧 grant 扩大读取范围 |
| 编辑已派发/部分落盘 | 用预先持久化的逐文件前后图像对账并完成一次 | 对不匹配的第三种内容强行覆盖 |
| 命令已派发 | 核对受管容器身份，保存原日志/回执并清理 owned 容器 | 猜测成功、重复启动、清理其他任务容器 |

应用编辑前写入 intent 和内容哈希；多文件应用中断时，各文件只能等于已记录的前图像
或后图像。先核对整组，再补齐缺失后图像；冲突必须保留，不把部分结果当成功树。
外层工具回执只有在对应内层编辑/命令已对账后才能成为 known。

命令仍经 H04 Broker/H06 CommandSession；容器身份绑定 task/run/operation/epoch/workspace。
开发者故障脚本可以操纵其专属测试进程与容器，不向项目模型增加 subprocess、Docker、
socket 或其他执行旁路。清理需验证完整 owned 标识，不能仅按名称前缀删除。

## 日志、上下文与终态

日志保留生成时的原 lease、grant hash、epoch、来源树与完整性信息。恢复已知基线回执
不重新归档到新 lease；更换或收窄租约后，不得通过新租约读取旧范围内容。
`artifact_hash`、cursor 与 checkpoint 不授予访问权。进程内原文索引不能凭历史文本恢复
授权；旧引用不可用时，应在当前许可下重新读取源码，旧日志继续遵守生成租约限制。

中途指令由 PG inbox 保存，只有包含该指令的 checkpoint 被选中后才能推进水位。
崩溃在“已应用指令/尚未保存 checkpoint”之间，需从旧水位重新应用一次；已存水位内的
指令不得再追加。恢复运行时的目标必须包含之前已保存的指令，再追加新消息。

H10 F01 终态规则继续适用：验证回执、必需验收项、diff、上下文与最终树必须一致。
旧树的绿色回执不能使新树 completed；树不稳定、unknown、待清理命令与必需 pending
项不能伪装为完成。Engine 的最终结果提交再次核对当前 epoch 与已记录树。

## 使用现有恢复入口

由现有服务启动流程持有 Engine 并完成启动对账后，对同一 task 发起已存在的 API：

~~~bash
curl --fail-with-body --silent --show-error --request POST \
  --header "X-MGAR-Token: ${MGAR_LOCAL_TOKEN:?请在本机安全加载令牌}" \
  "http://127.0.0.1:18080/api/v3/harness/tasks/${MGAR_TASK_ID:?请设置原任务ID}/resume"
~~~

令牌不得写入报告、命令输出或 Git。端口按现有部署配置调整。浏览器继续使用现有会话
与 CSRF 校验。服务内部复用 `HarnessCodingService.recover_task`；没有新建项目执行入口。
若返回 `RECOVERY_BLOCKED`、`USAGE_UNKNOWN` 或树冲突，保留任务、预占和原证据，先核对
明确的缺口，不能手工改 PG/CAS 为成功后再 resume。
