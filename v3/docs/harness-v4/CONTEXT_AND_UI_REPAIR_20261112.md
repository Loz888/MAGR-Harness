# 在线上下文与界面修复（2026-11-12）

用户要求：完成H12基线修复后，解决在线约8次工具调用后停止、增加按Adapter/API能力
选择上下文与分级压缩策略，并整理左上角布局。基线修订准备单独提交于`f32bad6`，
H12质量门仍需新独立持出集与真实模型实验，不能用本修复的工程测试替代。

## 已核实的原因

在线PG只读记录显示，最近两次GitHub分析均在8次工具调用后以`INPUT_TOKEN_BUDGET`
停止，模型调用4次/5次，累计输入28917/32770，累计输入与总Token授权均为60000。
上下文构建使用UTF-8字节/3估算，Adapter预检使用完整UTF-8字节保守上界；构建器
没有在派发前压缩到后一边界。前端又把累计输入额度误称为上下文窗口预算。

H12聚合还复现一项8K窗口的原文重读失败：引用重复携带相同任务/工作区/验收修订。
匹配的字段现继承外层WorkingState，旧修订仍显式保留；完整持久状态、每个引用和哈希
不删除，Registry仍对每次重读检查当前权限。旧表示恢复与原失败用例均有回归。

## 实现

- `context/policy.py`声明自动/自定义窗口，默认65%开始压缩、85%强制压缩、50%目标。
  目标＜准备＜强制；自定义窗口不能大于API能力，需留出输出、协议和最小输入空间。
- GitHub分析在每次派发前按与Adapter一致的序列化UTF-8上界核对，受模型窗口、剩余
  累计输入及总Token共同约束。按当前完整状态重新构建摘要；强制阶段缩短最近窗口，
  不回收已用额度、不丢证据ID和权限、不增加模型/工具次数或费用授权。
- 项目助手取消固定32K输入窗口，依据冻结模型能力、策略、输出预留和实现上限计算；
  65%/85%阈值在模型安全点执行，完整最新工具交互和受保护状态仍必须保留。
- 达不到50%但必要信息能放入硬上限时继续执行并记录真实大小；必要信息本身仍超限
  时保留结果并说明停止原因。压缩不是绕过累计预算的手段。
- 配置加密保存在原设置版本，冻结到每轮请求；保留旧配置的序列化/授权哈希，不新增
  迁移，不修改Engine持锁连接、结算算法、ToolAuthority或SA接线。
- 模型设置增加可选的窗口/阈值面板。顶部标题与模式切换独立布局，窄屏分行，去掉
  重复模式标记；项目操作分行；侧栏有关闭按钮、Escape和焦点返回。
