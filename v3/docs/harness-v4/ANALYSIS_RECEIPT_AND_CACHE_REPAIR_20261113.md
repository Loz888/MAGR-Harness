本文件保留`be99000`交付时的历史策略和证据。用户随后明确要求未决用量也可在同页

旧未知调用不重发、预占不清零，新用户问题沿原会话记忆在剩余总额度内执行。

用户报告：页面反复出现`Cannot set properties of null (setting 'textContent')`；
询问项目框架已有正确草稿，但Run显示失败，随后追问又被旧调用阻塞。

## 已核实的根因

1. 用户页面仍显示旧脚本的“已使用…Token”。当前页面已移除`composer-hint`，旧脚本
   `updateMode`仍对其写`textContent`。旧脚本与新HTML组合可在浏览器确定复现该异常。
   HTML虽为no-store，未版本化的静态JS仍可能被浏览器缓存，导致两者混搭。
2. 实际Run `40361dba-c4ad-4764-8850-f7afdbbd9584` 的失败码是
   `MODEL_RESPONSE_LIMIT`。12次工具读取全部成功，前7次模型调用已结算；第8次已有
   公开草稿增量，却没有保存模型回执或完成结算。该错误来自原Engine的256KiB回执
   保存上限，分析流式接收上限却是512KiB。SSE分帧封装可能远大于合并后的正文。
3. 保存回执的DomainError未正确收尾结算，遗留第8次call为reserved：US$0.016137、
   29213 Token预占。已结算US$0.009674；30505 Token不含这次未确认用量。后续追问
   的未决调用守卫因此阻止新派发，不能把该情况持续描述成“等待正在结束”。

完整回执未落盘，因此历史第8次的实际usage无法由现有草稿还原；不伪造费用、
不清零预占、不将原失败改为成功，也不自动重发旧调用。

原始只读PG核对见`evidence/harness-v4/ANALYSIS-FAILURE-20261113/run-audit.json`。
该轮冻结累计Token上限仍为60000，但本次失败码与该限额无关。

## 修复范围

- 页面将CSS、主脚本及产品脚本的内容SHA256加入URL，升级自动得到新缓存键；
  HTML继续no-store，原CSP/登录/来源权限规则保留。HTML与脚本还有UI契约检查，
  缺失关键DOM或版本不匹配时提示刷新并停止初始化，避免循环空节点异常。
- 分析适配层把完整SSE合并为有界的公开completion回执，保留模型、usage、必要
  公共输出及原wire的字节数/哈希；不将私有推理写入新增回执，不扩大Engine上限。
- 已得到完整有效用量时，即使回执处理或结果校验失败，也沿原账本如实结算；
  用量缺失则保留unknown和预占，避免遗留“看似仍在运行”的reserved调用。
  完整用量在退出HTTP上下文前核定，连接关闭失败也不能抹掉已收到的有效回执。
- 终态遗失回执返回明确的未决用量原因，区别于仍在结束的调用；页面展示具体失败码
  和预占，停止无用的终态详情轮询。已有未知用量继续需要供应商回执核对；也可由用户
  新建独立分析，保留原记录。
- 针对窄问题，提示模型依据直接相关清单/入口收敛，不要求无关全仓库调查；引用与
  答案覆盖验证继续执行，不能靠跳过验收或硬编码本仓库框架取得通过。
